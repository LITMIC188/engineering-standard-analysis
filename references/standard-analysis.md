# 标准文档解析与工程语义规则

## 处理步骤
- 登记文件哈希、标准号、完整年份/版本、语言、页数、页码偏移、正文缺失及可用附件；记录检索范围和是否缺少规范性引用文件。
- 提取标题层级、章/节/条、规范性与资料性附录、表、图、脚注、说明/例外及引用；原文段落保留 source span。
- 将原文“规定项”拆分成原子要求（例如每个工况、每个验收准则）；每项建立稳定 `requirement_id`，一条原文可拆多项，多条原文也可共同支撑一个任务。
- 将术语定义、引用、适用范围与技术要求分离；不能把建议性设计优化当成强制项。
- 对每个参数至少标明数值原文、单位、比较符、条件、零件/试样、来源；必要时把换算结果放派生字段，保留原始数据。
- 对标准对比，先检查适用范围、年份和规范性引用是否等效；再比较新增/删除、变更、重编号、放宽/加严、测试步骤/条件与验收准则变更。
- 最终报告把“标准明确要求 / 方案明确写明 / 工程建议 / 未核实问题”明确区分，输出来源与人工审核状态。

## 按页校验特别项
- 标题与页码匹配，表头跨页延续，图内标注、上下标、负号及小数点；涉及数值强制查看原页。
- 若文件不完整、不同语种版本术语冲突、规范性引用不可获取，在对应条款和方案审查中标记 `not_assessable`。
- 检索结果不能替代完整的章节及附录覆盖清单；不允许依据其他标准的相似数值回填当前标准。

完整原文的重建和冻结执行 [source-pipeline.md](source-pipeline.md)。标题从实际源语登记表得到，clause_id/heading_id/block_id分别保存；内部ID不能代替标题。章节/附录/表图/引用库存须与实际已核验原文相符，不能通过缩小预期清单制造完整性通过。

`compare --mapping <file>`只接受审核者明示的一对一旧/新requirement_id映射，记录 renumbering/amendment 和review_record；自动输出差异及needs_review，保留两版来源，不推定技术等效。跨标准、拆分/合并要求和适用范围变化由工程人员复核，不能仅用文本相同宣布相同义务。
